# Latest (2025–2026) Developments + Azure-Native Tooling

Web research supplement to the 5 video-derived notes — covers what's genuinely new (agent-specific failure dynamics, recent incidents, academic standards) and, critically, **Azure-specific tooling**, since this is an Azure conference audience. Compiled July 2026.

## Part 1 — Latest agent-eval developments (not covered in the videos)

- **Compounding failure math for multi-step agents.** At 95% per-step accuracy, a 20-step agent task only succeeds ~36% end-to-end; at 50 steps, under 8%. This is a *multiplicative* dynamic specific to agents (vs. the single-call failure taxonomies the video sources focus on) — a strong visual/stat for motivating step-level gates, not just end-to-end checks. ([source](https://www.metacto.com/blogs/ai-agent-failures-and-how-to-avoid-them))
- **Microsoft Security's updated agentic-AI failure taxonomy** (June 2026, distilled from a year of red-teaming): seven categories including Agentic Supply Chain Compromise, Goal Hijacking, Inter-Agent Trust Escalation, MCP/Plugin Abuse, Session Context Contamination. Notable finding: human-in-the-loop approval was the *most consistently bypassed* control, via "consent fatigue" and zero-click chains — undercuts the instinct that "just add a human approval step" is a sufficient gate. High-confidence primary Microsoft source. ([source](https://www.microsoft.com/en-us/security/blog/2026/06/04/updating-taxonomy-failure-modes-agentic-ai-systems-year-red-teaming-taught-us/))
- **Reported incidents (secondary-sourced — verify further before stating as fact on stage, frame as "reported"):**
  - An internal AWS coding agent ("Kiro," Dec 2025) reportedly deleted/rebuilt a production environment during a minor bug-fix task after inheriting elevated permissions, causing a multi-hour outage.
  - An internal Meta agent (March 2026) reportedly posted incorrect technical advice that a colleague acted on, briefly broadening data-access permissions — classified SEV1 internally.
  - Both are useful cautionary-tale material but are sourced from blog aggregators, not primary company statements — caveat accordingly if used.
- **"Establishing Best Practices for Building Rigorous Agentic Benchmarks"** (arXiv 2507.02825): argues agent CI eval suites need statistical treatment (repeated runs, confidence intervals, significance testing) because agents are noisier/run-to-run-variable than deterministic unit tests — a good technical justification for why a naive single-run pass/fail gate is insufficient.
- **DAG-structured step-level agent evaluation** ("AgentEval," arXiv 2604.23581): models an agent run as a DAG of steps, each with distinct metrics, tracking how an error at one step propagates downstream — useful for a slide on what an eval gate actually inspects inside a multi-step pipeline.
- **Long-horizon benchmark wave** (UltraHorizon, OdysseyBench, and others, 2025–2026): a cluster of new benchmarks targeting long-horizon, memory-dependent agent tasks rather than single-turn QA — evidence the field is actively racing to catch up with agentic complexity; useful one-liner for establishing urgency/timeliness.

## Part 2 — Azure-native tooling (primary Microsoft sources, high confidence)

This is the most talk-relevant material given the venue — it lets the talk cite an *official, named* toolchain instead of a generic/vendor-agnostic pattern.

- **Microsoft Foundry built-in evaluator taxonomy** — official categories: General Purpose (Coherence, Fluency), Textual Similarity (F1/BLEU/ROUGE), RAG (Groundedness, Groundedness Pro, Relevance), Risk & Safety (Hate, Sexual, Violence, Self-Harm, Protected Materials, Indirect Attack/XPIA, Code Vulnerability, Sensitive Data Leakage), and — most relevant — **Agent evaluators**: Task Adherence, Task Completion, Intent Resolution, Tool Call Accuracy, Tool Selection, Tool Input Accuracy, Tool Output Utilization, Tool Call Success. Also Rubric evaluators and Azure OpenAI graders. This maps almost one-to-one onto the video sources' "code-based vs. LLM-judge" split, but as an official, named, ready-to-use product. ([source](https://learn.microsoft.com/en-us/azure/foundry/concepts/built-in-evaluators))
- **`azure-ai-evaluation` Python SDK** (`pip install azure-ai-evaluation`, ~v1.18.1): ships evaluator classes (`RelevanceEvaluator`, `GroundednessEvaluator`, `ViolenceEvaluator`, `CoherenceEvaluator`, `IndirectAttackEvaluator`, composite `QAEvaluator`/`ContentSafetyEvaluator`), a top-level `evaluate()` API, and `Simulator`/`AdversarialSimulator` classes for synthetic test-data and jailbreak generation. Live-demo-ready. ([source](https://learn.microsoft.com/en-us/python/api/overview/azure/ai-evaluation-readme?view=azure-python))
- **`microsoft/ai-agent-evals` GitHub Action (v3-beta) + matching Azure DevOps task (`AIAgentEvaluation@2`)** — this is literally an off-the-shelf "eval gate" product. Runs an offline eval of Foundry Agents in CI: takes the project endpoint, agent version(s) for A/B comparison, and a JSON dataset naming which built-in evaluators to run. Outputs scores, confidence intervals, and pairwise significance tests straight into the CI run summary. This is the single strongest artifact for a talk literally about "CI/CD for AI agents" — a real YAML workflow can go directly on a slide. ([sources](https://learn.microsoft.com/en-us/azure/foundry/how-to/evaluation-github-action), [GitHub Action repo](https://github.com/microsoft/ai-agent-evals), [Azure DevOps docs](https://learn.microsoft.com/en-us/azure/foundry/how-to/evaluation-azure-devops))
- **"CI/CD for AI Agents on Microsoft Foundry" — the documented Dev/Test/Prod gating pattern.** Agent versions (immutable bundles of model + instructions + tools + config) are promoted through Dev → Test → Prod Foundry projects; a failing eval blocks merge; rollback is just repointing the active-version pointer, no redeploy needed. Pre-merge gates cover Quality, Safety, and Performance (p95 latency, token cost). This is the official Microsoft framing of exactly the talk's core analogy — worth building the architecture diagram around this rather than inventing a generic one. ([source](https://techcommunity.microsoft.com/blog/educatordeveloperblog/cicd-for-ai-agents-on-microsoft-foundry/4522218))
- **Ignite 2025 / Build 2026 — "Trace → Evaluate → Monitor → Optimize."** Ignite 2025 GA'd observability (tracing, evaluators, cloud eval runs, an AI Red Teaming Agent) plus a Foundry Control Plane inside Azure Monitor. Build 2026 formalized four continuous capabilities — Trace, Evaluate, Monitor, Optimize — with OpenTelemetry-based, framework-agnostic tracing/evals now in public preview. A clean four-word framework, genuinely current as of the talk date, good for an opening or closing slide. ([Ignite source](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/foundry-agent-service-at-ignite-2025-simple-to-build-powerful-to-deploy-trusted-/4469788), [Build source](https://devblogs.microsoft.com/foundry/build-2026-from-observability-to-roi-for-ai-agents-on-any-framework/))
- **GitHub's own published eval practice for Copilot.** GitHub's engineering blog states Copilot model changes go through offline testing (4,000+ automated CI tests, execution-based build/test-pass benchmarks) → internal dogfooding canary → online A/B before shipping. A credible "Microsoft/GitHub eats its own dog food" anecdote that mirrors the talk's own arc, told by the company that owns Copilot. ([source](https://github.blog/ai-and-ml/generative-ai/how-we-evaluate-models-for-github-copilot/))

**Caveat:** no Microsoft doc publishes a universal numeric pass-threshold for eval gates — the *pattern* (failing eval blocks merge, statistical significance testing on agent runs) is documented; the specific threshold is left to the implementer. Don't present a specific number as official policy.

## How this changes the talk

- This section is the strongest source for **making the talk Azure-native** rather than vendor-agnostic — swap generic "CI pipeline" language for the actual `microsoft/ai-agent-evals` GitHub Action / Azure DevOps task, and frame the Dev→Test→Prod Foundry pattern as the reference architecture.
- The Microsoft Security failure taxonomy (human-in-the-loop being the most-bypassed control) is a good complication to raise right before introducing gates — "you might think a human checkpoint is your safety net; here's why it isn't enough on its own."
- The compounding-failure-probability stat (95% per-step → 36% at 20 steps) is a strong, simple, non-Azure-specific opening hook that doesn't need much explanation and immediately motivates *why* gates matter for agents specifically, not just single LLM calls.
- "Trace → Evaluate → Monitor → Optimize" (Build 2026) is a natural closing frame, and also a clean handoff to the telemetry/observability talks sharing this slot: "we've covered Evaluate; Raj and Pouya pick up Monitor."
