# Why AI evals are the hottest new skill for product builders
Speakers: Hamel Husain & Shreya Shankar | Lenny's Podcast | ~1h46m | YouTube

## Core thesis
Evals are systematic data analytics applied to LLM applications — not exotic new machine learning, but a rediscovery of decades-old data-science and qualitative-research practices (error analysis, open/axial coding) applied to stochastic AI systems. The single highest-leverage activity in building an AI product is manually reading your own traces before writing any tests. Good evals grow bottom-up from observed failures in real data, not top-down from a checklist imagined before shipping. The goal isn't methodological purity — it's actionable product improvement, done cheaply enough that teams actually keep doing it. Much of the public "evals are useless / evals are essential" debate is really a semantic disagreement — nearly everyone serious about AI products is doing some version of this, whether they call it evals, dogfooding, or data science.

## Key frameworks / mental models
- **Error analysis workflow (the core loop):** read raw traces → open coding (freeform notes on what's wrong) → axial coding (cluster notes into named failure-mode categories) → count frequency (pivot table) → prioritize → build targeted evaluators → wire into CI/monitoring → repeat periodically.
- **Evals as a spectrum, not a synonym for "unit tests":** the big misconception is collapsing "evals" down to test suites. The full spectrum includes code-based assertions, LLM-as-judge, product usage metrics (thumbs up/down, engagement), cohort/distribution-shift detection, and online production monitoring.
- **Open coding vs. axial coding** (borrowed from qualitative/social-science research, not invented by them): open coding = quick freeform notes on the *first, most upstream* problem you notice in a trace (don't try to catalog every issue in one trace). Axial coding = later synthesis step where an LLM (or human) clusters the open-code notes into a smaller taxonomy of named, actionable failure modes.
- **Theoretical saturation:** stop reading traces once you stop learning anything new — not a fixed number. They suggest ~100 traces as a psychologically unblocking default, but the real stopping point is when notes stop surfacing new categories; with practice you develop intuition for it (sometimes as few as 15–40).
- **The "benevolent dictator" model:** open coding should be owned by one trusted domain expert (often the PM), not a committee. Consensus-building at this stage is expensive and unnecessary; you're optimizing for fast, tractable signal, not perfect agreement.
- **Code-based evals vs. LLM-as-judge:** use cheap deterministic code checks (is it valid JSON, is it markdown, is it short) wherever a failure mode is programmatically checkable; reserve LLM-as-judge for narrow, specific, subjective failure modes that can't be captured in code.
- **LLM-as-judge design rules:** always binary (pass/fail), never 1–5 or Likert — scores like "3.2 vs 3.7" are meaningless and Shreya calls Likert-scale judges an anti-pattern to actively fight. Each judge should be scoped to exactly one narrow failure mode, not general "quality."
- **Judge alignment / trust calibration:** never ship an LLM judge without validating it against your own human-labeled axial codes first. Build a confusion matrix (human label × judge label) and iterate on the judge prompt until off-diagonal disagreement is minimized. A single "agreement %" number is dangerous/misleading because rare failure classes let a judge get high agreement just by always saying "pass" (analogous to accuracy on imbalanced classes). This traces back to Shreya's research paper "Who Validates the Validator?" and the concept of criteria drift — people's definitions of "good" keep changing as they see more outputs, which is why you can't fully specify a rubric up front.
- **Evals-for-products vs. evals-for-models:** foundation-model benchmarks (MMLU, HumanEval, generic hallucination/cosine-similarity scores) are necessary for labs but largely uncorrelated with product-specific failure modes (e.g., a leasing bot mishandling human handoffs). Product teams need their own application-specific evaluators grounded in their own traces, not borrowed generic metrics.
- **Prioritization discipline:** you don't need an eval for everything. Typical mature products end up with only ~4–7 LLM-judge evals total — most discovered failure modes are just fixed directly in the prompt/code; you only build a durable automated evaluator for the "pesky," recurring, or business-risky failures that keep resurfacing.
- **Who should write evals:** the domain expert, not necessarily an engineer — often the PM. Coding agents are a special, non-generalizable case because the "user" (the engineer) IS the domain expert and is dogfooding constantly all day, so the team can short-circuit a lot of the formal error-analysis process — this is why Claude Code / coding-agent teams can plausibly say "we just go on vibes" while still implicitly doing rigorous error analysis (usage monitoring, internal escalation queues, dogfooding).
- **AB testing framed as a subset of evals, not a rival:** an AB test just compares a metric across two conditions — but you need error analysis to know the metric/hypothesis is grounded in real observed failures rather than a guess. AB tests run "hypothetically" without prior error analysis are a common anti-pattern.
- **Common anti-patterns called out explicitly:** trying to have an LLM do open coding/error analysis for you (LLMs lack the tacit product context to spot real failures — a demoed hallucination about a "virtual tour" passed as fine when checked with plain ChatGPT); using vague/lazy open-code notes like "janky" that can't later be auto-categorized; blindly trusting judge output as gospel without alignment checks; skipping straight to writing tests/evals before doing any data analysis; treating "we dogfood" as sufficient without actually doing it at a visceral, systematic level; premature/ungrounded AB testing.
- **Org process point — evals as "living PRD":** the LLM-judge prompts end up encoding actual, continuously-updated product requirements derived from real data — richer and more accurate than a PRD written before anyone saw real outputs. They argue this should feed back into (not replace) the traditional PRD process.

## Concrete examples / case studies discussed
- **Nurture Boss (the central case study):** an AI assistant for apartment property managers (leasing, customer service, tour booking) across chat/text/voice, using tool calls and RAG. Hamel walked through live traces from their real (anonymized) system prompt in an observability tool (Braintrust; alternatives mentioned: Phoenix/Arize, LangSmith). Specific failures found live: (1) an unhelpful "we don't have that, have a nice day" response to an availability question that a human would say should hand off differently; (2) garbled/broken conversation flow from a text-message channel splitting a user's sentence across turns; (3) the AI hallucinating that virtual tours were offered when they weren't — flagged as a clear case an LLM grader would have missed without domain context; (4) a call abruptly "transferred" to a human with no explanation given to the user. These became open codes, then were clustered via an LLM (Claude/ChatGPT/Julius/Gemini) into axial codes like "tour scheduling issues," "human handoff issues," "formatting errors," "conversational flow," "unfulfilled promises."
- Hamel then built a binary LLM-as-judge for the "human handoff" failure mode, showed the actual judge prompt (listing concrete triggering conditions like explicit human request ignored, sensitive issues, tool data unavailable), and validated it against the human-coded axial labels using a spreadsheet confusion matrix.
- A recruiting-email-sending AI client example: the AI was technically "doing everything right" (correct info, correct link, correct name) but Hamel, applying a critical product lens, flagged the email's generic tone ("given your background...") as something a recipient would dismiss/delete — illustrating that "technically correct" and "actually good" diverge, and that this critical judgment is exactly what error analysis is for.
- **Andrew Ng's error-analysis teaching (8-year-old video)** cited to show error analysis isn't a new invention — it's classic ML/data-science practice being reapplied to LLM systems.
- **Shreya's "Who Validates the Validator?" paper** (research from late 2023, before evals was a mainstream term) — user studies with experienced LLM-pipeline builders showed people cannot fully specify grading rubrics up front; their definitions of "good" shift as they see more outputs ("criteria drift").
- **The public Twitter/X debate** referenced: claims that Claude Code "doesn't do evals, just vibes" vs. praise for how eval-driven OpenAI Codex supposedly is — used to illustrate how inconsistent and context-free hot takes about evals are, and that coding agents are a special case (see above) not a generalizable model.
- **OpenAI's Statsig acquisition** discussed briefly and speculatively — framed as more about experimentation infrastructure than a referendum on evals; they note OpenAI has reportedly gone beyond eval benchmarks to mining Twitter/Reddit sentiment post-launch.

## Practical takeaways / how-to steps
1. Instrument your app with tracing/logging (any observability tool: Braintrust, Phoenix/Arize, LangSmith) so you can see full traces of prompts, tool calls, and outputs.
2. Read raw traces yourself (or have one trusted domain-expert "benevolent dictator" do it) and write short freeform notes ("open codes") on the first/most upstream thing that seems wrong in each trace. Don't try to catalog every error per trace.
3. Do this for roughly ~100 traces as a default target, but really stop once you hit theoretical saturation (no new categories emerging).
4. Feed the open-code notes to an LLM and ask it to synthesize them into a taxonomy of "axial codes" (failure-mode categories) — iterate on the categories yourself; don't accept the first output blindly. Include a "none of the above" bucket to catch incompleteness.
5. Use an LLM to re-classify all open-code notes into the finalized axial codes, then pivot-table/count frequency to see which failure modes are most common or most business-critical.
6. Triage: for failures that are obvious engineering mistakes (e.g., missing formatting instructions), just fix the prompt/code directly — no eval needed. Only invest in a durable automated evaluator for recurring, ambiguous, or high-risk failure modes.
7. For evaluable failures, choose code-based checks where possible (cheap, deterministic); use LLM-as-judge only for subjective/complex cases, scoped to one failure mode, always binary (pass/fail).
8. Before trusting a judge, validate it against your human-labeled data: build a confusion matrix, and iterate on the judge prompt until misalignment (off-diagonal cells) is minimized. Don't rely on a single aggregate "agreement %."
9. Wire validated evaluators into CI/unit tests (regression protection before shipping) AND into ongoing production monitoring/dashboards (sampling live traces daily/weekly) — these are complementary, not either/or.
10. Repeat the whole loop periodically (many teams do a lightweight version weekly, ~30 minutes, after an initial 3–4 day intensive first pass) — it's a one-time-ish setup cost with cheap maintenance afterward.
11. Build or vibe-code lightweight custom internal tools/UIs to make trace review as frictionless as possible for your team — worth the investment given how high-ROI this activity is.

## Notable soundbites (paraphrased, not verbatim)
- Evals are arguably the single highest-return activity you can spend time on when building an AI product — and once people start doing this loop, they get hooked on it.
- The goal was never to run a perfect evals process — it's to make concrete, actionable improvements to the product.
- People sour on evals not because evals are bad, but because they did evals badly once (usually a Likert-scale judge that didn't match reality) and generalized from that bad experience.
- The most common misconception is thinking that in the "age of AI" you can just point a model at your outputs and have it grade itself for you — it doesn't actually work, because the model lacks your domain and product context.
- Don't build a committee to review your traces — pick one person with real domain expertise you trust, a "benevolent dictator," or the process becomes too expensive to sustain.
- A Likert-scale judge score like "3.2 versus 3.7" is essentially meaningless — force yourself to make the harder binary call of pass or fail instead.
- Claude Code claiming to "just go on vibes" is misleading — it's really benefiting from foundation-model eval work by colleagues plus constant internal dogfooding and monitoring, which is itself a form of error analysis; that pattern doesn't generalize to non-coding AI products where the builder isn't the end user.
- Coding agents are a poor template for the rest of the industry because developers are unusually well-equipped to dogfood and judge code quality themselves — most domains (e.g., medicine) don't have that luxury.

## Anything conference-talk-relevant
- **Strong "unit tests are not enough" framing**: Hamel explicitly rejects the "evals = unit tests for LLMs" metaphor early on — useful contrast for a talk about moving from unit tests to eval gates: unit tests check known, non-negotiable functionality; evals also have to surface *unknown-unknowns* via open-ended data analysis, which is the genuinely new skill.
- **"Evals are the new PRD" framing** (Lenny's phrase, echoed enthusiastically by both guests) — a good analogy/soundbite for a CI/CD talk: the LLM-judge prompt becomes a living, continuously-updated executable spec of what "correct" behavior means, derived from real data rather than imagined upfront — a nice bridge from "PRD as static doc" to "PRD as always-running gate."
- **The AB-test-vs-eval "debate" is a strawman** worth debunking in a talk — AB tests need a metric, and eval work is what grounds that metric in reality; without error analysis first, AB tests are just testing hypotheses no one validated.
- **The "criteria drift" concept** (from Shreya's paper) is a great mental-model/soundbite for why you can't write your eval gate specs once and be done — rubrics have to evolve as you see more real traffic, directly supporting a talk point about evals/gates needing continuous iteration, not a one-time setup.
- **Concrete cost/time numbers** are talk-gold: ~3–4 days of intensive initial error analysis, dropping to ~30 minutes/week of maintenance; typical mature product ends up with only 4–7 LLM-judge evals total — useful for countering the "evals are too expensive/slow" objection in a CI/CD pitch.
- **Coding-agent dogfooding as a cautionary generalization** — useful talk beat: "just vibe-checking" scales for developer tools because devs are the domain experts constantly in the loop, but this doesn't transfer to most AI products (customer service, healthcare, real estate) — a good way to preempt the "but Claude Code doesn't need evals" pushback when pitching CI/CD eval gates for agents.
- **The "benevolent dictator" and taxonomy-building process (open coding → axial coding → counting → gating)** maps naturally onto a CI/CD pipeline diagram: manual review stage → categorization/taxonomy stage → automated regression tests (code-based gates) → LLM-judge gates for subjective checks → production monitoring dashboards — could be visualized directly as a pipeline analogous to build → test → deploy → observe.
- **Myth to bust:** "AI can eval itself, so I don't need a human in the loop" — repeatedly named as misconception #1 by both speakers, directly relevant to a talk about why eval gates still require deliberate human-curated ground truth before they can be trusted as automated CI/CD gates.
- **Binary-only judges as a design rule for CI gates** — directly reusable for a "how to write eval gates" section: gates should output pass/fail, not fuzzy scores, or the CI signal becomes uninterpretable (nobody knows what a 3.2 vs 3.7 threshold means for blocking a merge).
