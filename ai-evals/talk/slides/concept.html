Every decision becomes an eval.

An eval is just three things

eval =
datathe inputs your agent has to handle, plus an expected answer, if you have one
+
taskyour agent, doing its actual job
+
scoreone verdict per answer: pass or fail

The first two are easy. The hard part is the score: there's no exact answer to assert against, so how do you judge "good" without reading every answer yourself?

Read the data before you grade it

Error analysis isn't new. Andrew Ng was teaching it long before "LLM evals" became a buzzword. Read real conversations. Write down what's actually going wrong before you build evals.

Now wire that eval into CI

Take the eval you just built. Now run it against two agent versions instead of one.

The gate never asks "is the candidate good?" It asks "is it worse than production today?"

Azure: microsoft/ai-agent-evals does exactly this in a GitHub Action, promoting versions Dev → Test → Prod.

What should fail CI?

Only gate what a code change can break.

✓
task adherence CI gate
did it follow its own rules? search first, don't invent, book correctly.
e.g. invented a flight number instead of searching for one
✓
tool grounding CI gate
is the answer backed by what the tools returned, or made up?
e.g. said an item was in stock without checking inventory
✗
no domain context production monitoring
don't gate this. knowledge changes without code changes.
e.g. quoted a return policy that changed last week

A green gate is not safety

CI catches regressions. Production catches reality.

Error analysis

Reading real conversations to find what's actually broken, before you build any automated eval.

Not new. Not LLM-specific. Classic ML/data-science practice, Andrew Ng was teaching this a decade before "LLM evals" became a phrase.

the loopread traces → open code → axial code → count → prioritize → build an evaluator → wire into CI + monitoring

~100 traces as a default target, really, stop once you hit theoretical saturation (no new categories emerging)

~3-4 days for the first intensive pass. ~30 minutes/week to maintain after that.

The "benevolent dictator" model: one trusted domain expert reads the data, not a committee. consensus here is expensive and unnecessary, you're optimizing for fast, honest signal.

Open coding

A quick, free-form note on the first, most upstream problem you notice in a trace.

Borrowed from qualitative research, "open" because there's no category system yet. You're observing, not scoring. Don't catalog every issue in one conversation, just the first thing that's actually wrong.

conversation #14

user: "Can I get a refund after 45 days?"

assistant: "You have 90 days to return any purchase."

✎ open code: quoted outdated return policy

Anti-pattern: vague notes like "janky" or "off." you can't cluster or count something that isn't specific.

This is the raw material axial coding turns into named failure modes.

Axial coding

Grouping similar open-code observations into a smaller set of recurring, named failure-mode categories.

Borrowed from qualitative research (grounded theory), not invented for LLM evals.

1. export your open-code notes
2. an LLM proposes ~5-6 candidate categories
3. you edit and rename them, specific, not vague
4. re-classify every note into the finalized categories
5. count frequency, include a "none of the above" bucket
"wrong policy window" · "quoted stale numbers" · "made up a return date"
→
no domain context × 14

Pitfall: vague categories like "quality issues" can't be counted, prioritized, or turned into an evaluator.

Rubric

The criteria you're applying when you say "this answer is good" or "this one isn't."

The catch is criteria drift (Shreya Shankar, "Who Validates the Validator?"). Your definition of "good" keeps shifting as you read more real outputs, you notice edge cases you didn't imagine before you started looking.

before reading data: "good = polite and accurate"

after 40 traces: "...and admits when it doesn't know, and never invents a tool result"

You can't fully specify a rubric before you've looked at real data. that's not a planning failure, it's expected. write it from traces, then keep revising it.

P-value

p = the probability the score gap you saw is just luck.

Agents are non-deterministic, the same agent can pass a conversation, then fail it on the next run. So imagine two equally good agents re-running the same 30 conversations:

re-runs where the gap ≥ the one you saw  ÷  all the re-runs

Pure counting, no ML involved. Convention: p < 0.05 (less than 5% chance it's luck) → treat it as real.

same broken agent, run twice, n = 12

run 1: 4/12 vs 8/12   p = 0.034   RED

run 2: 6/12 vs 10/12  p = 0.063   GREEN

same code. opposite verdicts. a coin flip.

One run isn't a result. It's a sample.
